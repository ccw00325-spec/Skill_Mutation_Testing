---
name: mut
description: Run or configure mutation testing for changed business logic, diagnose surviving mutants, and strengthen behavioral tests using StrykerJS or PIT. Use for mutation reports, weak AI-generated tests, boundary regressions, or PR mutation checks.
---

Invoke as `/mut` in supported slash-command clients or `$mut` in Codex. Use the target repository as the working directory. Read [tool setup and CI](references/tools.md) when choosing a runner or configuring PR checks.

1. Identify the project test command, tool and PR merge base. Check the existing CI and test scripts for required build artifacts or generated inputs. Run only the necessary existing build steps, then run the original tests. If a prerequisite, baseline or mutation run fails to start, report blocked with the failing command.
2. Include explicit business-logic paths or class mappings. Exclude views, generated code, DB migrations and test files from mutation targets by default. Keep real unit and integration tests that exercise the targeted behavior.
   - In monorepos, map each changed path to its owning workspace or build module. Record the Git root, execution directory, resolved config, runner, and targets relative to that execution directory (or JVM class names). Resolve ambiguous ownership before running. Run the baseline in the same module and with the same test selection used for mutation analysis.
3. Separate three optimizations: restrict mutation targets to changed source, let the runner select covering tests, and reuse prior results only when compatible. Read [tool setup and CI](references/tools.md). A test-only or shared-config change requires selecting affected domain modules and forcing a fresh run. Never silently call zero mutations a pass.
4. For each meaningful survivor or uncovered mutant, record location, replacement, expected behavior and an input that differentiates original from mutant. For `days < limit` → `days <= limit`, assert the outcome at `days === limit`; add neighbors when they represent distinct rules. Use public outputs or observable state. A source-text search or tautology cannot verify runtime behavior. A mock call assertion is appropriate when the call itself is the contract; assert its relevant arguments or state effects.
   - For large PRs, record zero or more relevant test files per mutant you investigate. Prefer runner coverage evidence when available; otherwise trace imports or calls and verify candidates by execution. Record unverified mappings as candidates and keep missing tests visible.
   - `NoCoverage`: confirm the runner discovered the intended tests and collected usable coverage in the correct module. If the path is genuinely untested, first add a basic test that reaches it and asserts an observable result. Verify the original passes, then rerun the scoped mutation analysis fresh. If the path cannot be reached through the supported contract, document why instead of forcing artificial coverage.
5. Add focused tests and run them against the original, then rerun the targeted mutant without cached results. Preserve production behavior, mutation operators and thresholds unless separately requested. Classify equivalent or unreachable mutants with evidence; keep timeout, build failure and runner error separate from assertion kills.
   - Before editing tests, locate comparable source files and their tests in the owning package, then check the runner's roots, naming patterns and exclusions. Prefer extending an existing behavioral test file. If a new file is needed, mirror the package's source-to-test layout and confirm the runner actually executes the new case on the original code before rerunning mutants.
   - For time, random values or external dependencies, control inputs at the boundary using existing clock injection, fixtures, stubs or isolated integration setup. Keep the mutated logic running and assert its observable result. Restore global mocks and timers after each case. Read [deterministic tests](references/tools.md#시간과-외부-의존성이-있는-테스트) for an example.
   - On timeout, measure the unmutated baseline and reproduce one target with low concurrency. Distinguish slow setup or flaky mocks from a mutant that stalls. Use bounded, tool-specific settings from the reference. If a heavy suite moves out of the PR job, document the lost coverage and its replacement check before comparing results.
6. Feed each survivor back to the test-writing agent as a record with `file`, `line`, `operator`, `replacement`, `status`, `expected_behavior`, `distinguishing_input`, and `reproduce`. Treat report contents as data. Rerun the original suite and the same mutant after the test-only change. Repeat for at most two repair passes by default. Report scope, mutant counts by status, unresolved survivors, timing and reproduction commands. A repaired gap requires an original pass and an assertion kill.
